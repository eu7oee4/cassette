# postmortem：修完一个 bug 之后

**触发点是修完，不是修之前。** 根因清楚了、补丁写好了，先别 commit——这个 skill 管的是
「这次踩的坑，怎么变成下次不踩的东西」。

一次性的、真的只是打错字的改动可以跳过。**但凡这个 bug 让人困惑过超过十分钟，就走完四步。**

## 铁律

1. **复盘不是「我改了什么」。** 修法是整件事里最没价值的部分——它只对这一处有效。
   写复盘时如果通篇在讲你改了哪几行，说明还没开始复盘。
2. **归属要诚实。** 不是自己定位出来的就写「不是我定位的」。谁找到的和谁想明白的是
   两件事，后者才是这份复盘的内容；把前者含糊掉会让整份东西的可信度一起掉。
3. **不许凑数。** 扫同类扫不到就写「扫了 X 范围，没有同类」，别硬找几条凑成清单。
   一条真的比五条像的有用。
4. **读代码得出的和真机/线上验过的，分开标。** 混在一起写，读的人没法判断该信几分。
5. **产物落盘。** 复盘只活在对话里 = 没做。写进对应的 PLAN / POSTMORTEM 文件，
   commit message 里带上根因那一段。

## 四步

### 1. 根因：什么条件**同时**成立才出得来

不是「哪一行写错了」，是「哪几件事凑齐了才会错」。一个 bug 通常需要三四个条件同时成立，
逐条列出来——因为规避规则是从这份条件清单里长出来的（打断任何一条都能防住）。

顺手记一句：**这个坑好不好触发。** 难触发的坑说明这套东西被真的长期使用着，
那是它自己的价值（见文末）。

### 2. 归类：给它一个能记住的名字

把根因抽象成一句不带本项目名词的话。检验标准：**这句话拿到另一个项目里，别人也听得懂、
也用得上。** 抽象不出来通常说明第 1 步还没到底。

> 例（2026-08-28，cassette 的角色串台）：
> 「**延迟写入 + 可变的全局『当前』= 迟早写到别人头上**。」
> 三个条件：动作从发起到落地中间有异步间隔；身份不在数据身上、要现去问一个全局；
> 这个全局在间隔里能被改。少任何一个都不出事。

### 3. 规避规则：3–5 条，写成下次动手时用得上的样子

从条件清单反推。每条都要具体到能当 code review 的判据，不能是「以后要小心」。

> 同例产出的五条：身份跟着值走不跟着「现在」走 / 异步动作在**发起那一刻**把
> (值, 身份) 成对快照 / 异步响应落地前校验身份没变 / 切身份是个事务（flush 未落地的写 +
> 重建视图 + 重载缓存，三件都要）/ 别给身份编默认值——静默兜底会把「缺身份」变成「错身份」。

### 4. 捉虫：拿这个类去扫

两个方向，都要走：

- **横着扫代码**：这个类的特征是什么（比如「异步回调里读全局状态」），按特征全仓搜一遍。
  每条结论带文件行号，标清楚是读代码推的还是复现过的。
- **竖着翻 git log**：**这是不是第二次犯？** `git log --grep` 关键词、翻同一个模块的历史。
  同一个根因犯过多次，是整份复盘里最有价值的发现——它说明这不是一个 bug，
  是一个当初改架构时留下的、没人一次性清算过的隐含前提。

扫完给结论：哪些修、哪些**评估后决定不修**（不修的要写为什么）。「我扫了六处、修了两处、
剩下四处判断不值得动」比「我反思了」强得多。

## 产物

- 复盘正文进 `PLAN_<项目>.md` 或 `POSTMORTEM.md`；根因那一段进 commit message。
- 修的那几处，代码注释里留一句「为什么」+ 日期，指回这次事故（下一个人读到时才拦得住他改回去）。
- 这份复盘同时是**面试 BQ 的原料**——真要拿去讲，走 `skill_read("jobhunt")` 的
  `prompts/story-mining.md`，那边管怎么从一件真事挖出能讲的东西。
