# project-writeup：项目经历怎么写才有亮点（草稿版，跑完第一个岗后回来修）

触发：「这个项目怎么包装」「毕设怎么写进简历」「项目描述太平了」「开源项目怎么写」。
产出：简历里的**一段项目条目**（写回母版或定向版走 resume-tailor 的落库）。

**核心原则：项目是背景，你做的事才是主角。** 背景不超过两成，你做了什么占八成以上。

## 同一个项目，三种产物，一个真相源

| 产物 | 长什么样 | 谁管 |
|---|---|---|
| 简历版 | 一段：一句背景 + 三四条「行动 → 方法 → 成果」 | 本篇 |
| 讲稿版 | 五段口述：开场句 → 背景与问题 → 你做了什么 → 结果 → 与本岗位的连接 | interview-manual |
| 故事版 | 一件真事挖到「我从中带走了什么」 | story-mining |

真相源是 `resume/master.md` 项目节 + `stories/`。**源改了三个产物都要重出，别各写各的**——
不然三份会飘（09-01 那次「drift-bottles」就是抄了索引没回源）。

## 黄金结构（简历版）

```
[项目名]                              [时间]
[一句话背景：是什么、规模 / 用户 / 场景]  [你的角色]
[链接（有就放，即使 star 不多——证明真做了）]
负责工作：
• [行动 1]：[具体方法 / 技术] → [量化成果]
• [行动 2]：…
• [亮点]：解决了什么难题 / 做了什么取舍
```

## 先判项目类型，再挖亮点

**LLM / Agent 产品项目**（cassette 是这一类，产品线主打）
- 解决什么**具体**问题？不是「做了个 chatbot」。是「一个每天在用的 AI 陪伴产品，
  多角色 / 插件商店 / 长期记忆的信息架构」——写形态和为什么这么定，不写实现细节。
- 记忆 / 检索方案怎么设计的？评测怎么做（人工 / 自动 / 真机）？工具调用怎么设计（渐进披露）？
- **最独特的一条：自己每天在用**。写成事实句，不写姿态句。
- 数字用档案里 09-01 现查的那组（提交数 / 行数 / 测试数 / 插件仓数），**旧数作废**。
- 开发线投法：同一批东西写「实现了什么」（流式、MCP 工具链、长期记忆持久化）。

**嵌入式 / 实验系统**（狨猴平台）：架构、模块协同、稳定性怎么保证、专利进展。
**研究项目**（tACS）：方法、你负责的环节、竞赛结果。**这类别硬往产品岗凑**，一行带过即可。
**小程序 / 团队项目**：见下面「多人协作归因」。

## 多人协作怎么归因（她和 AI 协作也是这个问题）

用「我」不用「我们」。四种写法按清晰度排：
1. **功能模块归因**（最清楚）：「负责其中的 X 模块，独立完成 Y」
2. **比例归因**：「负责约六成后端接口（共 80 个，独立交付 48 个）」
3. **阶段归因**：「负责 0 到 1 的选型与架构设计，后由团队实现」
4. **角色归因**（最模糊）：「担任 X，负责方向决策和 review，团队 3 人」

**和 AI 协作的项目**：归属诚实反而加分（story-mining 纠偏 3）。写法是
「产品形态和信息架构是我定义的；实现由我和 AI 协作完成，我负责判断和验收」——
面试官分得清「会用工具」和「用完就走」。故事库里「三处归属待确认」就是这个问题，
写简历前先跟机主把归属问清楚，**不许替她判**。

## 教程项目 / 跟做项目怎么升级

改名不是重点，重点是**加了什么**（按含金量排）：部署上线有地址 → 加一两个自主功能 →
换一个技术选型并写清为什么换 → 优化一个指标写前后对比。不写「基于 XX 教程实现」。

## 开源贡献怎么写

可量化的按含金量：合并 PR 数和类型 → 解决的 issue 严重级 → 被 changelog 收录 →
仓库规模背书。只 star 过、只提过 issue 不列。**写之前点开确认署名是她**。

## 内部 / 涉密项目

写数量级不写精确值（「日均百万级」），公司名可替代（「某三甲医院」），
加一句「架构图可面谈展示」。

## 五个加分技巧

1. 有在线地址就放；2. 写选型理由（「选 X 不选 Y，因为场景需要 Z」）；
3. 写难点怎么突破；4. 写可复用价值（「被 N 个插件仓复用」）；5. 有 GitHub 就放。

## 输出格式

```
【原版】…
【改写版】…
【关键改动】1. … 2. …
【补上这些会更强】（需要机主提供的数据或细节，不编）
```

## 按岗位换重心（同一项目）

| 投 | 讲什么 |
|---|---|
| 产品 | 发现问题 → 定义方案 → 推动落地；用户在哪、为什么这么定 |
| 研发 | 技术选型 → 架构决策 → 工程质量 |
| 运营 | 冷启动 → 增长 → 数据 |
| 管理 | 资源协调 → 对齐 → 交付节奏 |

## 写法口味（档案 09-01，写任何一段都生效）

不写卖弄的话；项目条目只写清架构和特点，「为什么」留给面试官挖；
不写「数月」「长期运行」；外部验证类条目先点开原始出处。
