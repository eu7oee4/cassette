# interview-manual：面试手册（主菜；草稿版，跑完第一个岗后回来修）

输入：JD（`jd_read`）+ 简历（`resume_read`）+ 公司情报（`intel/<公司名>.md`，
没有就先走 `prompts/company-intel.md`）+ 相关项目的真实材料（代码/文档，能读就读）。
产出：一个岗位的手册**内容**（结构化 markdown）——成品形态是网页工作台，
内容做完后 `skill_read("workbench")` 走交付层渲染。

> 成品深度 **09-14 机主拍板：可以慢慢啃的长文档**，不是一页带进考场的精简版。
> 展开细节可以写满、写透；每节开头仍留一句「考场句」当索引和临场提示，
> 但它是入口不是天花板。工作台的折叠结构正好承载。

## 手册骨架（机主 08-27 定的三大块）

### 1. 公司情报层
从 intel 文件浓缩：业务一句话、这个岗在解什么问题、面试官可能是谁、近况。
每条保留证据档位标注；inferred 的口碑只进「心里有数」不进「开口就说」。

### 2. 岗位匹配层（逐条过 JD）
把 JD 拆成条目，每条三分：
- **能打**：有真实素材直接对上 → 链到故事/项目，配一句考场句
- **可迁移**：没干过一模一样的，但有可类比的 → 写清类比逻辑（这是最容易临场卡壳的）
- **缺口**：真没有 → 想好被问到怎么答（承认 + 学习路径），**不许包装成「能打」**（铁律 1）

每个重点条目配「可能追问」2–3 条。项目讲稿用五段结构：开场句(1) → 背景与问题(2-3) →
你做了什么(3-4，聚焦你的决策不是团队的) → 结果(1-2) → **与本岗位的连接**(1-2)。
口述配比和一稿多用见 `frameworks/star-car.md`——最常见的死法是背景讲一半时间。
能力标签统一用 `frameworks/competency-tags.md` 那十二个，反查故事库靠它。

### 3. 反问清单
从 intel 的「反问素材」出 3–5 条，按对象分（HR 面 / 业务面 / 老板面）。
好反问的判据：答案会改变你对这个岗的判断，而不是显得你有准备。

## 流程

1. 先查 `stories/_index.md`（铁律 2）：能复用的素材先标出来，缺口记成「待挖」清单——
   那是 story-mining 的输入，**不在手册流程里现场编故事**。
2. 逐节产出，素材不足的地方写 `待补`，回问机主，不许编（铁律 1）。
3. 手册内容落 `state/jobhunt/manuals/<岗位>.md`，然后走 workbench 交付。
